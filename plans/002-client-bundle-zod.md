## Why this matters

`src/lib/registry.ts` validates the built catalog with zod at module scope:

```ts
export const registry: Registry = registrySchema.parse(catalogJson)
```

`registrySchema` comes from `shadcn/schema`, whose implementation chunk
(`node_modules/shadcn/dist/chunk-4WBGNKSZ.js`) begins with `import {z as z$1} from 'zod'`.
And `src/lib/registry.ts` is imported by components that run in the browser —
`src/components/docs/sidebar.tsx:3` and `src/routes/index.tsx:7`. So zod, the
whole shadcn registry schema, and the 23 KB catalog JSON are all downloaded,
parsed and executed by every visitor, and the `.parse()` runs a full schema
validation of 26 items during hydration on every page load.

That validation buys nothing at runtime. The catalog is generated by
`pnpm registry:build` from files in this repo, and that script *already* runs
`shadcn registry validate` as its first step (`scripts/build-registry.mjs:29`).
Data the project generates and validates in CI does not need re-validating in
the user's browser.

After this plan: `shadcn/schema` is a type-only import in the app, so it is
erased at compile time and leaves the client graph entirely — while the
validation guarantee moves to the build script, where a failure stops the build
instead of being discovered by a visitor.

exactly where the check belongs.

### Conventions to honor

- `tsconfig.json` sets `"verbatimModuleSyntax": true`, so type-only imports
  **must** use `import type`. A plain `import { Registry }` will fail
  typecheck. Line 2 already does this correctly.
- `tsconfig.json` sets `"resolveJsonModule": true`, so the JSON import has a
  structural type inferred from the file. It will not be assignable to
  `Registry` directly; a double assertion is required (see Step 1).
- `scripts/` is in the ESLint `ignores` list (`eslint.config.js`), so the build
  script is not linted — but keep its existing style: ESM, double quotes, no
  semicolons, and the `step(name, fn)` helper for each phase.
- Prettier does not format `scripts/` either (the `format` script globs
  `**/*.{ts,tsx,js,jsx,mjs}`, which *does* include it — run `pnpm format` and
  accept its output).

## Steps

### Step 1: Record the "before" measurement

You need a before/after to prove the change worked. The shadcn schema chunk
contains a unique literal string, `Registry URL must include {name} placeholder`.
If that string is in the client assets, the schema (and therefore zod) shipped.

```bash
pnpm build
ls -d .output/public
grep -rl "Registry URL must include" .output/public
```

Record what the `grep` prints. It **must** match at least one file right now —
that is the defect. If `.output/public` does not exist, STOP and report the
actual layout of `.output` (the check needs to target client assets only; the
server bundle legitimately contains the schema and is not the problem).

**Verify**: `grep -rl "Registry URL must include" .output/public` prints one or
more file paths.

### Step 2: Make `shadcn/schema` type-only in `src/lib/registry.ts`

Delete line 1 (`import { registrySchema } from "shadcn/schema"`) and replace
the `.parse()` with an assertion, updating the doc comment to say where
validation now lives:

```ts
import type { Registry, RegistryItem } from "shadcn/schema"

import catalogJson from "../../public/r/registry.json"

/**
 * The built catalog (`public/r/registry.json`) is the single source of truth
 * for the docs site: sidebar, search, item pages and llms.txt all read it.
 * It is imported statically so it ships with both the server and client
 * bundles. Run `pnpm registry:build` to regenerate it from the source registry.
 *
 * Deliberately not parsed with `registrySchema` here. That pulled zod and the
 * whole shadcn schema into the client bundle to re-validate our own build
 * output in the visitor's browser. The catalog is validated against the same
 * schema in `scripts/build-registry.mjs`, where a failure stops the build.
 */
export const registry = catalogJson as unknown as Registry
```

The `as unknown as Registry` double assertion is required: `resolveJsonModule`
gives the import a structural type that TypeScript will not narrow to
`Registry` directly. Keep the rest of the file byte-identical.

**Verify**: `pnpm typecheck` → exit 0, and
`grep -n "registrySchema" src/lib/registry.ts` → no matches.

### Step 3: Move the validation into the build script

In `scripts/build-registry.mjs`, add a validation step for the built catalog
immediately after it is read. Add the import at the top of the import block:

```js
import { registrySchema } from "shadcn/schema"
```

and change the catalog read (currently `const catalog = JSON.parse(...)`) to
validate it, using the existing `step()` helper so it prints like every other
phase:

```js
const catalog = JSON.parse(readFileSync(path.join(outDir, "registry.json"), "utf8"))

// The docs site consumes this file as trusted, typed data (src/lib/registry.ts)
// rather than re-parsing it in the browser. This is where that trust is earned.
step("validate built catalog", () => registrySchema.parse(catalog))

const items = catalog.items ?? []
```

Note `step()` is a function declaration at the bottom of the file, so it is
hoisted and callable here.

**Verify**: `pnpm registry:build` → exit 0, and the output contains a line
reading `▸ validate built catalog`.

### Step 4: Prove the validation actually fires

Temporarily corrupt the built catalog and confirm the build fails:

```bash
node -e "const f='public/r/registry.json';const fs=require('fs');const c=JSON.parse(fs.readFileSync(f,'utf8'));c.items[0].type='not-a-real-type';fs.writeFileSync(f,JSON.stringify(c,null,2))"
node scripts/build-registry.mjs
```

This must fail with a zod error. Note `pnpm registry:build` would rewrite the
file before validating, which is why this step calls the script in a way that
still re-reads the corrupted file — if `shadcn build` overwrites the corruption
and the command succeeds, that is fine too: it means the pipeline is
self-healing. Either outcome is acceptable; what is **not** acceptable is the
script completing while `registrySchema.parse` is absent.

Restore the file afterwards, whatever happened:

```bash
git checkout -- public/r/registry.json
pnpm registry:build
git status --porcelain public/r
```

**Verify**: `git status --porcelain public/r` prints nothing (the regenerated
output matches what is committed).

### Step 5: Confirm the schema is gone from the client bundle

```bash
pnpm build
grep -rl "Registry URL must include" .output/public || echo "CLEAN"
```

**Verify**: prints `CLEAN`. If it still prints file paths, the module is
reaching the client through a path you have not accounted for — run

not, fix it; if all are and the string persists, STOP and report.

### Step 6: Final checks

```bash

pnpm registry:check
pnpm typecheck
pnpm lint
```

**Verify**: all four exit 0.

## Maintenance notes

- The load-bearing rule is: **`src/lib/registry.ts` must never import a runtime
  value from `shadcn/schema`.** It is imported by client components, so any
  value import there drags zod back into the browser. The Done-criteria grep is
  a cheap CI guard if someone wants to add one.
- `src/start.ts` also imports `registry`. That file is server-only, so it is
  unaffected either way.
- Deliberately deferred: moving `shadcn` from `dependencies` to
  `devDependencies`. After this plan the app no longer imports any shadcn
  *runtime* code, but `src/styles.css` imports `shadcn/tailwind.css` and the
  build script executes `node_modules/.bin/shadcn`, so the reclassification
  needs its own verification pass.
- A reviewer should scrutinise: that the `as unknown as Registry` assertion is
  justified by a build-time validation that genuinely runs (Step 3's output
  line is the evidence), not merely asserted away.
